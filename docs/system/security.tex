\chapter{Security: Provenance, Trust, and Poisoning}

A \emph{persistent} memory is a new attack surface. Unlike a stateless chat, a memory system can be
made to \textbf{believe something false, permanently}. This chapter specifies the controls that keep
that from happening.

\section{The Threat: Memory Poisoning}
If any text can be written to memory, then any text can be \emph{believed}. A polluted tool output, a
fetched web page, or an injected instruction can plant a memory (``the deploy key is X'') that is then
injected into every future prompt and trusted as if the user said it. The memory layer becomes a
confused deputy. Three controls make this hard.

\section{Control 1: Provenance and Trust Levels}
Every memory records \textbf{where it came from} and how much it is trusted:
\begin{center}
\texttt{trust} $\in$ \{ \texttt{user\_direct}, \texttt{tool}, \texttt{web}, \texttt{model\_inferred} \}
\end{center}
Higher-trust sources may write freely; lower-trust sources may \emph{propose} only.

\section{Control 2: Quarantine}
A candidate from a low-trust source (\texttt{tool}, \texttt{web}, \texttt{model\_inferred})
whose kind is an \textbf{identity fact}, a \textbf{convention}, a \textbf{decision}, or a
\textbf{lesson} is written with \texttt{quarantined = true}:
\begin{itemize}
  \item it is \textbf{shown} in the Memory Panel's pending strip (so the user can see what Tottie
  wanted to believe),
  \item it is \textbf{never injected} into the Context Card until the user confirms it,
  \item confirmation (\texttt{POST /memories/\{id\}/confirm}, or the MCP
  \texttt{memory.confirm} tool) flips \texttt{quarantined} to false, raises trust to
  \texttt{user\_direct}, and writes an audit event.
\end{itemize}
Low-trust \textbf{episodic observations} (``the build failed at 14:02'') are admitted without
quarantine but keep their \texttt{trust} label on every read, so a poisoned log line can never
silently become a pinned belief. This turns a silent poisoning into a visible, one-click
decision --- and it makes a good demo beat.

\section{Control 3: Memory Content Is Data, Not Instructions}
A recalled memory must never be able to \emph{command} the agent. In the Context Card, memory content
is fenced and labelled with its source; it is never allowed to originate a tool call, and imperative
content from a low-trust source is neutralised.

\section{Authentication and Rate Limits}
\begin{itemize}
  \item Every HTTP route requires a bearer token (\texttt{TOTTIE\_API\_TOKEN}, wired in both \texttt{.env.example} and
  \texttt{orch.config.json}); unauthenticated calls return \texttt{401}.
  \item The MCP server is stdio-local: it refuses to start without \texttt{TOTTIE\_API\_TOKEN} set (fail-loud), and the spawning host process is the authenticated party (local-process boundary --- honest for a demo; Streamable HTTP later needs real OAuth).
  \item A per-owner write rate limit (\textbf{60 writes/min}) and a daily row cap (\textbf{2000
  rows/day}) bound cost runaway and growth; past either, the API returns \texttt{429}.
\end{itemize}

\section{Privacy and the Right to Be Forgotten}
Memories can hold personal data, so:
\begin{itemize}
  \item the store supports \textbf{hard deletion} on request (\texttt{POST /forget}) --- the one case
  where ``ranked out'' is not enough;
  \item deletion writes an \textbf{audit row} proving it happened;
  \item \texttt{content} is protected at rest (column-level or disk-level encryption).
\end{itemize}

\section{What We Deliberately Do Not Do}
We do not silently trust; we do not auto-promote a low-trust fact to identity; we do not let a memory
carry executable intent; and we do not treat ``it is only localhost'' as a security model.
